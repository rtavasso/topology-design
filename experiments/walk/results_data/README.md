# E1–E4 results kept in git

The full raw results are too large for git (repo convention: large artifacts go outside it). This folder keeps enough to check every number in [../RESULTS.md](../RESULTS.md) and the ledger, and to run new reanalyses of the trajectories.

**What is here**

| file | contents |
|---|---|
| `eN_summary.md`, `eN_summary.json` | Output of `analyze.py eN`: the preregistered verdicts and tables, as reported. |
| `eN_runs.json.gz` | One record per run: `run_id`, full `config`, `n_params`, the run's `summary` (including `prequential` for E1, `swap`/`jump` for E2), and a thinned `trajectory`. |
| `verification/` | The independent recomputation scripts behind RESULTS.md's "verification" sections (`e1.py`, `e2.py` for E1/E2; `e34_*.py` for E3/E4, including the matched-time reanalyses). They were written against the raw results and expect `results/kaggle_eN/results/`. |

**Trajectory thinning.** Every eval up to step 1,000, then every 500 steps, plus the last eval. Floats are rounded to 5 decimals. Kept fields: `step`, train/test accuracy and loss, `gen`, `mem`, `exc_acc`, `rule_frac_test`, `branch_rms`, the block- and branch-ablation `gen`/`mem`/test accuracy, and the E2 instruments (`refit_test_acc`, `ridge_test_acc`, `extrap_acc_1000`, `extrap_acc_4000`, `extrapd_acc_1000`). Dropped: per-parameter gradient and weight norms, and the other ablation splits.

What the thinning loses: the raw runs were evaluated every 10–25 steps early and every 100 steps later. E2's lead times were computed at that full resolution, so recomputing them from this copy past step 1,000 is coarser (500-step grid). Event times in each run's `summary` (`t_fit`, `t_grok`, stability flags) are exact.

**Where the full results are**
- On the researcher's Mac: `results/kaggle_e1` … `results/kaggle_e4` (and `results/kaggle_pilot`) in the repo checkout, gzipped JSON per run.
- On Kaggle, as the outputs of the kernels `riley9/topology-fleet-e1` … `-e4`.
