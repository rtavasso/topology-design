# Review 2 of the rung-1 design (revision 2, `84b4dbd`) and its code

Independent adversarial review, 28 Oct 2026, before the pilot. Read: DESIGN.md rev 2 (§15), review 1 (design, code), Entry 61, AGENTS rules 3–5; `route/{data,exec,router,train_route,train_neural,pool}.py`, `tests/test_route.py`, `make_grids.py`, `run_route.py`, `analyze.py`, `derive/*`, `ptr/stacked.py` (embed, FLAG_DIR). CPU checks (scratchpad `review2/`): `symonly.py` (hand-built policies on the repository executor), `smoke.py` (every trainer path for 20 steps, records through `analyze.py`), the 12 route tests (pass, 96 s), and the two-seed RM run started before this review (`rev2_cpu/`: batch 16, lr 1e-3, 1,500 steps = 24k episodes ≈ 6 % of the 6k × 64 budget; records `cpu_RM_s{0,1}.json.gz`).

**Verdict: run with changes.** The deferred trigger does what revision 2 says for the router (A.i, B): a setup step is required by the executor, its credit arrives through the exact marginal, and the rule is learned early in the budget. But three of the headline predictions are mis-specified in ways that are visible before any GPU step: P3's PP strata fail first on an untrained *precedence* decision, not on the count value 2 (finding 1; 2/2 CPU seeds); P5's premise that the looped block "must hold the pending bit across a loop" is false, because the deferred flag is readable in one attention by a value-slot match (finding 2); and P9's marginal line predicts the wrong quantity (finding 3). All three are text changes plus a few lines of recording; none changes training.

## Findings

**1. (blocking, design + ~15 lines) P3 tests precedence before it tests the count.** Under δ = 1, a flagged state entered with a pending count is *by construction* a PP run (flagged ⇒ the next exit is PREV; entered with c ≥ 1 ⇒ this exit is PREV), so training never shows the router a state where "flagged ∧ h = 0 ⇒ SET" and "c − h ≥ 1 ⇒ PREV" both fire. The oracle's order (SET first) is forced, and the router's choice there is untrained. The CPU run shows exactly this: at 1,500 × 16 steps, in-range `route_acc_P` is 0.94 / 0.82 (in8), alt4 1.00 / 0.93, deepP8 0.95 / 0.82, but **pp4 = pp6 = pp8 = 0.00 in both seeds, first deviation `SET>PREV` 40/40 and 31/40** — at (s_j, c = 1, h = 0, flagged), the router PREVs (the PREV column has norm 1.1 vs SET's 0.41). The c = 2 state is never reached, so the question P3 is built on (does PREV extrapolate along the count ray?) goes unmeasured, and the falsifier text ("PREV>HOP or PREV>SET at the c = 2 state; the count was read categorically") describes a failure that does not occur. RM-d0 passes pp trivially (every (c, h, flag) combination on its PP route is in support), so the planned RM − RMd0 contrast would be read as "categorical count" when it is "untrained precedence". Also the c = 2 states are not "never visited": off-route mass (SET at h = 1) reaches (flagged, 2, 1) in training; the signal there is small and sign-ambiguous (HOP better by 0.002–0.004 nats in nll, PREV better under the λ term; `symonly.py`), so not a strong push either way. **Change:** the router is evaluated at all 390 states, so add two counterfactual-state probes on in-range P-words to `evaluate` and the criterion curve: (a) argmax π at (s_{i−1}, 2, 0) — the oracle's P-leaving state with the count forced to 2 — equals PREV (the ordinal question, isolated); (b) argmax π at (s_{i−2}, 1, 0) — the flagged state with a pending count — equals SET (the precedence question). Restate P3 as two predictions with these as the measurements and pp as their conjunction; add the outcome rows "pp fails by (b) with (a) passing" (composition of two learned rules at a new conjunction: the module-network outcome at the level of rules) and "(a) fails" (the count is categorical). Both are informative; the current text would mislabel the likely one.

**2. (blocking, design + recording) P5's premise is wrong: the block need not carry the bit.** The flagged pair under δ = 1 is the one whose *value slot holds the P-leaving state's key*; a query holding s in its register finds it with one head (query = register on the value-slot subspace), reads the flag, and gates value vs prev in the same layer. This is the inference §2/§6 grant the symbol-only router, and the same generic match-and-read as HOP. A hand-built policy using exactly that feature reaches marginal accuracy 1.00 on in4–in8 P-words, len16 and alt8 (`symonly.py`, strata table). Ambiguity from decoys pointing at the same key (≈ 9 % of keys) is harmless in training because decoy-source pairs are never flagged without PP. So LF vs LF-d0 differs by one head, not by a loop of memory; "LF ≤ 0.6 on P-words, LF-d0 ≥ 0.2 better" is unsupported, and ¬P5 would not mean "the block holds the deferred bit in its stream". **Change:** relabel P5 as "a two-match gate learned in one block vs an explicit register" (still the open arm; the learned-circuits caveat of review 1 A.iii stands); drop or soften the LF-d0 margin; note that "memory inside the block" needs δ ≥ 2 (a countdown state; a follow-up design). Recording gap (unrecoverable later): `train_neural.evaluate` records `acc_at_k` / `acc_at_k1` / `acc_at_kP` over the whole stratum, not split by `hasP`; P5's clause "oracle-depth reading no better on P-words" cannot be read (confirmed on the smoke output: `analyze.py` prints `P5 LF@k acc@none8` only). Add `acc_at_k_P`, `acc_at_kP_P` (and surface `acc_at_kP` in `derived_rows`).

**3. (blocking, text) P9's marginal line predicts the wrong quantity, and the F4 reading needs a sentence.** With the stochastic trick (SET with probability a at a flagged pair, PREV at a symbol pointed at by a flagged pair), the argmax of the exact mixture is the target for **every a ≥ 0.3** — the wrong mass is spread over 15 answers and the keys — so `marg_acc_P` on in4–in8 is 1.00, not "0.3–0.8"; what lies in 0.3–0.9 is p(target) (0.31 / 0.50 / 0.64 / 0.64 / 0.51 at a = 0.3 / 0.5 / 0.7 / 0.8 / 0.9 with T = 14; 0.79–0.88 at T = 64). On the training objective (λ = 0.02, T = 14) the trick's optimum is a ≈ 0.7 at 0.144 vs the oracle policy's 0.070 nats per query, and its E[steps] on P-words exceeds the oracle's by only 0.46 there (the (1 − a) mass dies early on PREV), so the "≥ 1 per P-step" clause is borderline (2.7 / 7.8 at a = 0.8 / 0.9 on in4 at T = 64). **Change:** state P9's marginal line as `p_correct_marg_P` ∈ (0.3, 0.9) with `marg_acc_P` ≈ 1 and E[steps] above the oracle's (no fixed margin); record `p_correct_marg_P` (the P-split loop omits it). And say in "Reading the outcomes" what the explicit state buys at this rung: a deterministic program (committed 1 vs 0), about 2–3 fewer actions per P-step, and ≈ 0.05–0.07 nats of objective — not accuracy in the Bayes reading. A sampled-route reading (K samples through `committed` with sampling) would make the "0 by construction" line honest about a stochastic system; cheap, recommended.

**4. (non-blocking) B: reachability is not the obstacle; P1's ordering clause is wrong.** Analytically the SET share of the posterior at the flagged state under a uniform router is 0.32 at k = 3 and 0.13–0.17 at k ≥ 4 (vs prior 0.25), so the early gradient is weakly against SET on long words and for it on the dominant HPH — nothing like (1/4)³. Empirically (both seeds): HALT and HOP at ≥ 0.98 by step 100–200; **PREV (teacher-forced at the oracle's PREV state) is 1.0 from step 100**, because the posterior at (s_{i−1}, 1, 0) is sharp however little stray-SET mass arrives there; **SET crosses 0.5 at step 900 / 1,000** (≈ 4 % of the budget) and reaches 0.98 / 0.92 by 1,500. λ = 0.02 does not block the flip (a P-word gains ≈ 2.8 nats from SET). So P1's falsifier will not fire for an optimization reason, and "SET and PREV together within 300 steps" will be scored false for a mundane one: restate as "PREV first (sharp posterior), then SET; the SET flip time is the setup-credit measure, RM-T's SET flip the reference". p(HALT) at distance 0 / 1 / ≥ 2 is 1.00 / 0.00 / 0.00 already (P8 fine).

**5. (non-blocking) Code paths checked, all correct.** `exec.maps` / `oracle_policy` match §3 for both deferrals, including PP (c reaches 2 at (s_j, 2, 1), then PREV, PREV), PPP (a P-landing that is also flagged: SET then PREV; the cap at 2 never binds on an oracle route), and SET's no-op on answers / ⊥. `router.plant` encodes SET: flag − h, PREV: c − h·[δ = 1] − flag/2, with the LayerNorm scale differing by state (|x|² = 1 + c² + h² + f²); the tests cover it. `teacher_loss` / `action_accuracy` index the oracle route correctly (the per-episode alignment in `evaluate` relies on `sel[:, 0]` selecting one query per episode in order — fragile but right). `first_dev` reports late and early halts as `none>…` / `…>none`. `acc_at_k` uses `hs[0]` = after loop 1, so `at(k − 1)` is loop k: no off-by-one. Criterion seeds (s·7919 + 999) are disjoint from pool (+11) and strata (+12345) streams for every s. `analyze.py` consumes every field the eight trainer paths write (smoke); cosmetic: derived rows for LFd0 are labelled `LF@kd0`, `LF@T10d0`; P7's heading says 0.84 for both readings. Pilot/main grouping: lr sweeps stack, λ runs split (correct). Cost: 1 TFLOP per 10-stack step by count → 0.08 s per run-step is conservative. Memory: ≈ 3.5 GB of saved activations (six d-wide and two 2d-wide tensors over 250k state tokens) + 0.4 GB optimizer per 10-run stack at batch 64 in fp32: two stacks share a T4; measure in the pilot.

**6. (non-blocking) Outcome table.** Add: P1 ∧ RM-d0 failing pp or in-range (a bug or λ artefact; stop); P1 ∧ ¬P3 split by finding 1's probes; RM-s marginal ≈ RM marginal (finding 3's reading of F4); P5 with LF-d0 ≈ LF (finding 2: the trigger is locally readable). Deferring the planted-gate block (D99) is acceptable, and less costly than review 1 thought: under δ = 1 the block's task is a gate over two reads, close to what that arm isolates. Fairness items (per-arm lr from in-range accuracy at 4k, paired seeds, held-out criterion, S8 at 3 × 12k) are fine.
